## objective

Materialize the documented Pattern Registry definition as an explicit, versioned and runtime-validated domain contract without adding persistence, UI, workers or pattern detection.

## context

`ST-S01-001` established the executable TypeScript baseline and canonical event envelope. The next independent increment must remain inside `delmacy/system-trading` and implement the smallest documented registry contract. The source of truth is `docs/03-trading/PATTERN_REGISTRY.md`, supported by `docs/06-governance/VERSIONING.md`, `docs/02-architecture/DOMAINS.md` and `domain/ubiquitous-language.md`.

This task may run while the System Builder dogfooding gate is pending because it neither consumes nor changes Builder contracts.

## included scope

- create the minimal `trading-domain` workspace package if it does not exist;
- expose a public runtime schema and TypeScript type for a versioned Pattern Definition;
- cover the documented identity, description, family, version, eligibility, data requirements, deterministic criteria, parameters, tolerances, context indications, invalidation signals, references, status, authorship and detector association fields;
- model exactly the documented lifecycle values: Draft, Experimental, Validated, Active, Degraded, Deprecated and Archived;
- validate UUID identifiers, non-empty required strings, non-empty eligibility/data collections, UTC ISO-8601 authorship timestamp and semantic version syntax;
- add focused deterministic tests and public package exports;
- update only the minimum execution documentation and changelog needed for the new package.

- database, migrations, storage, API, UI or CLI;

- Strategy, Context, Experiment or Dataset registries;
- lifecycle transition rules not documented by the source material;
- System Builder workspace/capability provisioning;
- any Builder contract or file;

## architectural rules

- implement the documented Pattern concept directly; do not introduce a generic registry abstraction;
- keep the domain independent of vendors, databases and UI frameworks;
- use explicit boundary types and runtime validation;
- use UTC ISO-8601 timestamps;
- use `unknown` rather than explicit `any` for open structured values;
- do not invent lifecycle transitions or persistence semantics;
- published-version immutability remains a documented future repository concern, not a fake in-memory guarantee;
- do not weaken existing lint, typecheck, test or build gates.

## Contratos consumidos/alteraveis

- Consumed: the documented Pattern Definition and versioning rules in the System Trading repository.
- Alterable: only the new local `trading-domain` Pattern Definition contract.
- Frozen: `EventEnvelope` from `trading-protocols` and every shared System Builder contract, including `WorkspaceContext`, `AuthenticatedActor`, `DomainEvent` and `CapabilityDefinition`.

## acceptance criteria

- a public `PatternDefinition` type is derived from a runtime schema;
- every required field from the documented minimum structure is represented without persistence leakage;
- lifecycle accepts exactly the seven documented values;
- invalid UUID, invalid semantic version, invalid/non-UTC timestamp, empty required collections and missing required fields are rejected;
- a valid definition validates deterministically and preserves its value;
- tests demonstrate that open parameters/criteria use safe `unknown` values without explicit `any`;
- package exports do not expose internal paths;
- no generic registry, repository, database, UI, detector or Builder integration is introduced;
- the existing event-envelope tests continue to pass.
